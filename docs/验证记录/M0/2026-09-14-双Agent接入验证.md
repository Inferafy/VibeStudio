# M0 双 Agent 接入验证

验证日期：2026-09-14。

关联模块：[外部工具层：Agent 接入](../../模块设计/外部工具层-Agent接入.md)、[本地能力层：会话运行](../../模块设计/本地能力层-会话运行.md)、[本地能力层：Agent 原生能力](../../模块设计/本地能力层-Agent原生能力.md)。

验证结论：Claude Code、Codex 的 ACP 新建、恢复、加载历史和真实续聊均通过；原生 CLI 创建的专用会话也能由对应适配器恢复并继续原上下文。M0 要求的配置、命令、工具、审批、用量和取消边界已形成实测记录。

| 项目 | 固定值 |

Codex 沿用本机已有的 API Key 登录缓存，验证记录不包含密钥。Claude 以 `--hide-claude-auth` 启动，当前机器的非订阅认证路径可用；没有通过第三方客户端使用 claude.ai 订阅登录。

## 2. 隔离与安全

- 专用测试项目：`C:\code\VibeStudio-M0-Fixture`，单独初始化 Git，并带有探针要求的安全标记。
- 测试开始前项目干净；写入审批拒绝后，目标文件不存在，项目仍然干净。
- 探针默认将 Codex 切到 `gpt-5.6-luna`、Claude 切到 `sonnet`，思考等级均为低。
- 探针拒绝全部权限请求，没有批准真实写入或读取额外目录。
- 每次验证使用新的适配器进程。结束后按进程路径和创建时间检查，没有发现本轮遗留的适配器或 Agent 子进程。
- 没有删除、改写或迁移用户已有会话。

## 5. 采用 VibeX 的部分

实现前直接核对了 VibeX 固定提交 [`e30cb859`](https://github.com/Xircth/VibeX/commit/e30cb859c63e9436dc61cdc02d21c7756d4788ee)：

- 按 Agent 上报能力决定是否调用 `session/resume` 和 `session/load`。
- 恢复时继续使用外部原生会话标识和原工作目录。
- 优先恢复运行状态，加载历史作为带回放的路径。
- 会话建立前后的事件都按目标会话标识归属。
- 恢复期间的历史重放与新回合输出分开处理，避免重复写入业务历史。

VibeX 当时锁定 Claude 适配器 `0.69.0`、Codex 适配器 `1.7.0` 和 Rust ACP `1.2.0`，其真实探针只验证初始化握手。本项目保留它的运行思路，并用当前固定版本补齐 Windows 新建、恢复、加载、工具、审批和取消实测。

## 6. 已知边界

- Codex 使用 API Key 时，`/status` 会显示无 ChatGPT 账号，ChatGPT 套餐用量和限额不可用；上下文令牌用量仍可收到。
- Codex 的只读命令事件中观察到重复终端输出增量，后续按工具调用标识和增量顺序合并，不能把重复文本直接追加两次。
- Claude 的 `available_commands_update` 会在恢复后再次完整上报，客户端应替换会话命令快照。
- Claude 的用量事件在真实回合中出现过短暂归零，之后恢复为正确值；界面不能把中间的零直接当成上下文清空。
- Claude 的 `/context` 在本环境返回了两份相同展示内容；正式消息层需要依据消息标识和命令边界去重。
- `session/load` 会先回放历史。M0 探针通过回放静默窗口分离历史和新回复；生产实现应沿用连接恢复状态和事件归属分离，不能依赖固定等待时间。
- 模型和思考等级已验证“可读取、可设置”。跨多轮及跨进程是否始终保持用户选择，留到 M2 生命周期验证。
- Claude 首次基线会话在探针默认值收紧前使用了适配器当时的默认模型；随后探针固定为 `sonnet` 和低思考等级，恢复、原生会话、加载、工具、审批与取消验证均按该限制执行。
- 本轮没有实现终端、文件读写和表单提问等客户端反向能力，只记录为未声明；Agent 自身执行的工具事件已经验证。

## 8. 结论

M0 退出标准已经满足：两个 Agent 的当前固定版本均可在 Windows 上通过 ACP 新建会话、恢复 ACP 会话、恢复各自原生 CLI 会话、加载历史并继续真实上下文；配置、用量、命令、工具、审批和取消边界已有实测依据。
